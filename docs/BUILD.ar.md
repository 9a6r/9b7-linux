# تحويل المشروع إلى ISO

**حالة الإصدار:** الكود قابل للتطوير والاختبار، لكن لا يُسمّى ISO نهائيًا قبل اجتياز مصفوفة الإقلاع في `VALIDATION.md`. اقرأ `HANDOFF.md` للحالة الفعلية الأخيرة. لا تخلط بين نجاح اختبارات Python وبين إقلاع نظام تشغيل.

## جهاز البناء

- Linux x86_64، Docker يعمل أو Arch Linux أصلي. `mkarchiso` يحتاج root وmount؛ حاوية البناء تحتاج `--privileged`.
- يوصى 16GB RAM و100GB مساحة فارغة للنسخة الكاملة، ومعالج 4 أنوية. سكربت ضغط ISO يستخدم عاملين لحماية الذاكرة.
- الجهاز المستهدف 8GB RAM. هذا مختلف عن متطلبات تجميع كل الحزم والصور.
- تجنّب Docker driver `vfs` في بناء النسخة الكاملة؛ تكرار طبقات الصور قد يحتاج مساحة أكبر بكثير. استخدم Docker مع overlay2 على ext4.
- اتصال بمرايا Arch، GitHub، PyPI، Docker Hub، PortSwigger، وسجل Ollama. راجع نطاقات `NETWORK.md`.

## النسختان

| الاختيار | ما يتضمنه | أول تشغيل للخدمات |
|---|---|---|
| `full` | سطح المكتب، التطبيقات، صور الخدمات، نموذج Qwen 1.5B | بلا تنزيل إذا اكتمل التجميع والتحقق؛ يحتاج قرص بيانات للخدمات الثقيلة |
| `desktop` | سطح المكتب، التطبيقات، Studio وFlow وملفات الخدمات | الإنترنت مطلوب لتنزيل الصور والنموذج |

وفق خارطة التطوير الأخيرة، الأولوية لـ`desktop` وخدمات ونماذج عند الطلب على جهاز8GB. الأصل Full محفوظ؛ لا تعِد بناءه قبل نجاح Desktop. الحزم دون إنترنت يمكن توزيعها اختيارياً منفصلة لاحقًا.

## البناء من Linux مع Docker

نفّذ من جذر checkout المشروع:

```bash
docker build -t 9b7-builder -f scripts/builder.Dockerfile .
docker run --detach --name 9b7-local-builder --privileged -v "$PWD:/project" 9b7-builder sleep infinity
docker exec 9b7-local-builder bash scripts/build-extra-packages.sh
docker exec 9b7-local-builder bash scripts/build-desk-package.sh
docker exec 9b7-local-builder bash scripts/build-iso.sh desktop
```

صور Docker تُضغط مباشرة عند التصدير، ونموذج Qwen يُجلب من manifest مثبت وتُراجع بصمات كل ملف. يمكن إضافة `--remove-exported` إلى bundle-offline على **Docker مخصص للبناء فقط** لحذف الصور بعد تصديرها؛ لا تستخدمه على مخزن خدماتك اليومية. يحتاج السكربت Python مع PyYAML وDocker Compose وgzip.

النتيجة في `out/`: ISO، SHA256، قائمة حزم، ومرجع الكود. حزم Arch تُتحقق بتوقيعاتها؛ الحزم الإضافية بمراجع AUR مثبتة، checksums مصادر، وتوقيع مفتاح بناء محلي. المفتاح الخاص يبقى في `cache/signing` ولا يدخل Git أو ISO.

احتفظ بنفس الحاوية بين المراحل: بناء DEsk يعتمد على مستخدم البناء ومفتاح الثقة اللذين أنشأتهما مرحلة الحزم. بعد حفظ النتائج يمكن إيقاف حاوية البناء:

```bash
docker stop 9b7-local-builder
```

لا تشغّل `build-extra-packages.sh` على نظامك اليومي: يُنشئ مستخدم بناء وصلاحية pacman داخل بيئة البناء المخصصة. لا تحذف توقيعات أو تستخدم `--skippgpcheck` لعلاج فشل تنزيل.

في بيئة cloud ذات proxy بشهادة CA مُدارة، مرّر **الشهادة العامة الموثوقة التي توفرها المنصة** أثناء بناء الحاوية: `docker build --secret id=build_ca,src=/path/to/platform-ca.crt -t 9b7-builder -f scripts/builder.Dockerfile .`. لا تعطّل TLS. هذه الشهادة تخص أداة البناء ولا تُنسخ عمدًا إلى نظام اللاب النهائي.

## تشغيل البناء على GitHub

1. افتح [Desktop ISO - download preview](https://github.com/9a6r/9b7-linux/actions/workflows/desktop-download.yml).
2. لو تستخدم Fork في حساب آخر: افتح المستودع الخاص بك واضغط **Sync fork → Update branch**. من Actions داخل نفس الـFork افتح Workflow ثم **Run workflow → main**. استخدم تشغيلًا جديدًا؛ **Re-run jobs** يستخدم commit التشغيل القديم. يستخدم Ubuntu runner و`GITHUB_TOKEN` التلقائي الخاص بالمستودع الجاري؛ لا يحتاج PAT ولا يبني Full.
3. يبني الحزم وDesktop داخل حاوية Arch واحدة ويتحقق من SHA-256، ثم يحفظ **`desktop-iso-experimental-…`** في **Artifacts** لمدة **3 أيام**. هذا أسرع مسار لتجربة VirtualBox: نزّل ZIP، فكّه، واختر ملف `.iso`؛ لا تستخدم JOIN لهذه النسخة. معها ملف SHA-256 وقائمة الحزم ومرجع المصدر. بعدها يقلع ISO في QEMU بنمطَي BIOS وUEFI ويحاول الدخول عبر SDDM وبدء DEsk والتطبيقات. UEFI تعمل حتى لو فشل BIOS، ويظل الفشل ظاهرًا في نتيجة التشغيل. الصور والسجلات في `desktop-boot-evidence-…`، وحالة الاختبارين في Summary. ملفات الاختبار والنشر تُكتب في `RUNNER_TEMP` المملوك لمستخدم Actions، بعيدًا عن `work` الذي ينشئه builder بصلاحيات root.
4. بعد نجاح الفحوص، ينشئ **prerelease تجريبية** ويرفع ISO بأجزاء أقل من 2GiB مع البصمات وسكربتات التجميع، ثم يعيد تنزيل الأجزاء للتحقق من مطابقتها للأصل. يظهر رابط Release في **Summary**. إذا فشل التحقق يعيدها إلى مسودة ولا يعلن نجاح التسليم.
5. حمّل كل ملفات `.partNN` و`iso-parts.json` و`SHA256SUMS.parts` وملفات `JOIN`. ضعها في مجلد واحد به مساحة تكفي الأجزاء والـISO معًا. في Windows شغّل `JOIN-WINDOWS.cmd` مع وجود `JOIN-WINDOWS.ps1`، وفي Linux شغّل `bash JOIN-LINUX.sh`. لا تفك الأجزاء ببرنامج ZIP. السكربت يفحص البصمات ويترك ملف `.iso` الأصلي جاهزًا لاختياره في VirtualBox.

الفحص الآلي يثبت بدء الجلسة والعمليات؛ صور Plymouth وSDDM تحتاج مراجعة بشرية، ولا يعادل اختبار التثبيت أو VirtualBox أو الصوت والأجهزة الحقيقية. إذا ظهر فشل في Actions، حمّل سجل الخطوة وملف evidence؛ لا تعتبر مجرد وجود ISO نجاحًا للاختبار.

Artifact الخاصة بالـISO متاحة للتجربة اليدوية حتى لو فشل فحص QEMU لاحقًا، بشرط نجاح رفعها؛ هذا لا يحوّل الفشل إلى نجاح ولا ينشر Release معتمدة. تحتاج تسجيل الدخول إلى GitHub لتنزيل Artifacts. ملفات Release المقسمة متاحة بعد نجاح الاختبارين والتحقق من التنزيل. التشغيل القديم الذي انتهى قبل إضافة خطوة حفظ ISO لا يتيح استرجاع ملف لم يُرفع؛ يلزم تشغيل جديد بعد المزامنة.

Workflow القديم **Build ISO** محفوظ لمسار artifact والبناء المتقدم. Full تحتاج self-hosted runner و`bundle-offline.py` قبل البناء؛ تجهيزها مؤجل حتى الموافقة بعد تجربة Desktop.

## VirtualBox

1. أنشئ جهاز Linux / Arch Linux 64-bit، ذاكرة 4096MB، معالجين، VMSVGA، ذاكرة فيديو 128MB، واترك 3D acceleration مغلقًا كبداية.
2. أنشئ قرص VDI ديناميكي 64GB على الأقل؛ 80GB أنسب للخدمات الكاملة.
3. اختر ملف ISO كقرص optical. UEFI وLegacy BIOS مدعومان في profile، وكلاهما يحتاج اختبارًا فعليًا قبل الإصدار.
4. اختر **Live desktop** لتجربة DEsk؛ عند مشكلة الرسوميات اختر **Compatibility / XFCE**. شاشة الدخول: `9b7` / `9b7`.
5. استخدم **Install 9b7** لتثبيت نفس التخصيصات على الـVDI. بعد نجاح التثبيت أخرج الـISO وأعد التشغيل.
6. خصص 5–6GB للـVM إذا كنت ستعرض ERPNext، وأغلق البرامج الثقيلة على المضيف. لا تتوقع ERPNext وكل أدوات BI معًا على لاب 8GB.

## USB واللاب

- نفس ISO يصلح USB وVirtualBox. استخدم Ventoy أو Rufus بوضع DD؛ حرق ISO يمسح الفلاشة المحددة.
- عطّل Secure Boot لهذه النسخة؛ لا تتضمن سلسلة توقيع Secure Boot. لا تغيّر إعدادات firmware أخرى بلا داعٍ.
- اختر Live للتجربة أو Compatibility لو العرض الرسومي تعثّر. وجود NVIDIA قد يحتاج تعريفًا مناسبًا واختبارًا منفصلًا؛ لا ندّعي دعم كل كروت NVIDIA.
- جلسة Live مؤقتة. تشغيل Docker من ISO على جهاز 8GB يحتاج تخزين ext4 دائم للخدمات أو تثبيت النظام على القرص؛ مساحة RAM المؤقتة ليست مخزنًا مناسبًا لصور ERP.
- لو عندك قسم ext4 مركّب مسبقًا وبه 20GB+ فارغة: نفّذ `sudo 9b7-storage /path/to/mount` قبل تشغيل الخدمات. الأداة لا تفرمت؛ ترفض استبدال Docker store به بيانات. في كل جلسة Live جديدة أعد تركيب القسم وتفعيل المخزن نفسه. لا تعتمد على FAT32/exFAT كمخزن Docker.
- المثبت الحالي يمسح **قرصًا كاملاً** بعد كتابة `ERASE /dev/...`؛ ليس مثبت dual-boot. ابدأ باختباره على VDI فارغ، ولا تختبره على قرص عليه ملفاتك.

## خطوات قبول الإصدار

شغّل اختبارات الكود، ابن Desktop أولًا، تحقق من SHA256، اختبر BIOS وUEFI وVirtualBox، اختبر الإقلاع الثاني بعد التثبيت، ثم افصل الإنترنت واختبر كل خدمة منفردة. سجّل النتائج في `VALIDATION.md`. عندها فقط أنشئ Release باسم الإصدار وارفع الـISO وSHA256 وقائمة الحزم وملاحظات التراخيص.

## مساحة عمل منفصلة (متقدم)

لبيئة اختبار ذات RAM وفيرة وقرص صغير، يمكن تحديد `NINEB7_WORK_DIR=/path/to/work` على filesystem منفصل، و`NINEB7_BIND_OFFLINE=1` لربط الأرشيفات read-only داخل profile بدلاً من نسخها مرتين. يشترط السكربت مساحة عمل تكفي نسختين من الحزمة زائد 13GB، ومخرجات تكفي الحزمة زائد 5GB. استخدام tmpfs يحتاج RAM فعلية تكفي هذه المساحة مع بقية النظام؛ لا تستخدم هذا الأسلوب على لاب 8GB. هذا مسار متقدم قيد اختبار البناء، وليس تغييرًا لمتطلبات جهاز المستخدم.

## إعادة تجهيز Desktop محفوظة

`scripts/repack-desktop.sh BASE-desktop.iso PREPARED_ROOT NEW.iso` مسار متقدم
داخل Arch builder: يتحقق من بصمة الأصل ومرجع المصدر، ويرفض الكتابة فوق ISO
أو تضمين ملفات مستخدمين ومفاتيح البناء. يحتاج root مجهزة من الأصل، محدثة
بالـprofile الحالي، مع kernel/initramfs متطابقين. يعيد إنشاء EFI FAT بالنسختين
الجديدتين ويحدث SquashFS وبصمتها؛ يحتفظ بمعرّف الإقلاع الذي تبحث عنه القائمتان.
لا يثبت هذا السكربت نجاح الإقلاع؛ اختبر المخرج نفسه في BIOS وUEFI.

المثبت الرسومي في المصدر يطلب حسابًا جديدًا وكلمة مرور8حروف على الأقل،
ويمنع الحساب التجريبي من أن يكون حساب التثبيت الدائم. يمرر كلمات المرور
عبرpipe، ولا يحفظها في ملف إعدادات. لا توجد خاصيةdualboot. راجعVALIDATION
لمعرفة ما إذا اكتمل اختبار التثبيت والإقلاع الثاني للـISO الذي ستنزله.
